На входе `{"ean13": "590123412345"}` — 12 цифр. Программа рассчитывает контрольную цифру `7`, кодирует 95 модулей EAN-13 и строит SVG. В браузере виден штрих-код `5901234123457`. `barcode.py` делает расчёт и рисует полосы; `cli.py` читает файл и пишет SVG в стандартный вывод. Четыре разных входа:

## 2. «Найти в коде обработчик 4.1», этап 2

Это `POST /api/collect/report`. Покажи маршрут и реализацию:

```bash
rg -n 'collect/report|collect_report' src/practice2/routes.py src/practice2/model.py src/practice2/client.py
nl -ba src/practice2/model.py | sed -n '100,122p'
```

Объяснение: обработчик соединяет `Response.task = Task.uid` и `Task.member = Member.uid`, оставляет ответы с `Response.datetime > now - 540` секунд, делает уникальные тройки `[Member.ip, Response.duration, Task.tags]` и сортирует результат. Граница строгая: ровно девять минут назад исключается. Время исполнения `duration` хранится в миллисекундах. Соответствующий маршрут есть в `routes.py`, вызываемый метод — `Model.collect_report`.

## 3. «Найти и показать 2.1», этап 2

Это `PUT /api/save/task/:uid`. Покажи весь путь запроса:

```bash
rg -n 'save/task|save_task|class TaskScheduler|def start|def _complete' src/practice2
nl -ba src/practice2/model.py | sed -n '69,85p'
cat src/practice2/runner.py
cat src/practice2/server.py
```

`server.py` принимает HTTP-запрос и проверяет заголовки. `routes.py` сопоставляет адрес с `Model.save_task`. Модель проверяет `Member`, создаёт `Task` и ожидающий `Response`, после чего `TaskScheduler` отправляет расчёт в фон. Рабочий поток запускает **отдельный процесс** `python -m practice2.cli` через `subprocess`, затем записывает SVG и время завершения. Ответ на PUT приходит раньше окончания расчёта: в нём `completed=0`; итог читается отдельным GET. Имена `do_GET`, `do_POST`, `do_PUT` заданы интерфейсом `BaseHTTPRequestHandler` — это обоснованное исключение из snake_case.

### Живой HTTP-показ этапа 2: два терминала

В первом терминале из корня проекта:

```bash
mkdir -p data
FILE_DB="data/demo-file-$(date +%Y%m%d-%H%M%S).json"
./run.sh server --backend file --database "$FILE_DB"
```

Второй терминал тоже открой в корне проекта. Выполняй по очереди:

```bash
curl --noproxy '*' -sS -X PUT \
  'http://127.0.0.1:8024/api/save/member/1?ip=127.0.0.1&locale=ru' \
  -H 'Accept: text/json' -H 'Accept-Language: ru' | python3 -m json.tool

curl --noproxy '*' -sS -X PUT \
  'http://127.0.0.1:8024/api/save/task/1' --get \
  --data-urlencode 'member=1' --data-urlencode 'tags=ean13' \
  --data-urlencode 'input={"ean13":"590123412345"}' \
  -H 'Accept: text/json' -H 'Accept-Language: ru' | python3 -m json.tool

sleep 1
curl --noproxy '*' -sS \
  'http://127.0.0.1:8024/api/read/response?uid=1' \
  -H 'Accept: text/json' -H 'Accept-Language: ru' | python3 -m json.tool

curl --noproxy '*' -sS -X POST \
  'http://127.0.0.1:8024/api/collect/report' \
  -H 'Accept: text/json' -H 'Accept-Language: ru' | python3 -m json.tool
```

В `Response` ожидаются `status: "success"` и строка SVG с `5901234123457`. Если сразу видишь `pending`, повтори запрос `read/response`: это нормальное следствие асинхронности. `collect/report` покажет тройку с IP, длительностью и `ean13`. В первом терминале останови сервер `Ctrl+C`; затем можно показать `cat "$FILE_DB"`.

## 4. «Показать MBT и контрпример при внедрении ошибки в HTTP-клиент», этап 2

Покажи эталонную модель, проверки и зафиксированный контрпример:

```bash
cat tests/mbt_machine.py
cat tests/test_mbt_file.py
cat tests/test_mbt_tiny.py
cat scripts/show_mbt_counterexample.py
cat submission/Проверки/mbt_fault_explanation.txt
cat submission/Проверки/mbt_fault_counterexample.txt
make mbt-file
make mbt-tiny
```

`RuleBasedStateMachine` генерирует последовательности операций через настоящий HTTP-клиент и сравнивает сервер с независимыми словарями. Отдельно проверяются файловая БД и TinyDB. Положительные прогоны покрывают все девять маршрутов и 100% строк и ветвей `client.py`, `model.py`, `routes.py`, `server.py`.

Для воспроизведения ошибки без правки сдаваемого кода:

```bash
.venv/bin/python scripts/show_mbt_counterexample.py
```

Скрипт создаёт временную копию клиента и удаляет в `ApiClient.save_task` параметр `tags`. Модель ожидает переданный тег, поэтому Hypothesis сокращает сбой до `state.seed(ip='', tags='0')`. Внутри временного теста **ожидается** `1 failed`; сам демонстрационный скрипт после обнаружения ошибки завершится успешно. Он может работать около минуты. В чистом проекте ошибка отсутствует, и оба обычных MBT-прогона проходят.

## 5. «Показать файл базы данных на диске», этап 3

В первом терминале после остановки файлового сервера запусти TinyDB в новом файле:

```bash
TINY_DB="data/demo-tiny-$(date +%Y%m%d-%H%M%S).json"
./run.sh server --backend tinydb --database "$TINY_DB"
```

Во втором терминале повтори четыре `curl`-команды выше: создание `Member`, создание `Task`, чтение `Response`, отчёт. После `Ctrl+C` в первом терминале:

```bash
ls -lh "$TINY_DB"
cat "$TINY_DB"
python3 -m json.tool "$TINY_DB" | head -80
cat src/practice2/tiny_storage.py
```

В JSON-файле будут таблицы `member`, `task`, `response` с созданными документами и SVG в поле `response`. `TinyStorage` пользуется библиотекой TinyDB, реализуя те же `all`, `write`, `close`, что и `FileStorage`; код модели и API при смене базы не меняется.
